# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

NIND ("nouvelle indexation") is a flat-file inverted-index module originally built for the `Amose` search engine (replacing the deprecated `S2` and `Lucene` indexers). It has two parallel implementations of the same binary formats:

- **C++** (`src/cpp/`): the production indexing/search libraries.
- **Python** (`src/py/nind/`): an ergonomic Python frontend to the same binary formats. Historically written as a from-scratch pure-Python re-implementation of the C++ readers/writers (no shared code between the two) simply because no Python bindings existed yet — the low-level classes are being migrated onto the `nind._native` pybind11 bindings instead (see below), including their shared structural-diagnostic base (`analyseFichierPadFile`/`analyseFichierIndex`); the remaining per-format diagnostic/introspection methods stay on hand-rolled parsing until `nind._native` grows equivalents for them too (see "Planned follow-up work" below).

The Python package lives in `src/py/nind/` (moved there from `src/py/*.py` by the `refactoring-for-codecommons` refactoring, now merged into `master`), with the higher-level `nind_engine.py` (BM25-style search API) layered on top of the low-level Python classes.

The `nind` wheel additionally bundles a compiled extension, `nind._native` (pybind11 bindings over the core C++ index stack — `NindLexiconIndex`, `NindTermIndex`, `NindLocalIndex`, `NindRetrolexicon`, `NindLexicon`; full read/write) — see `src/cpp/NindPy/`. This is the intended long-term backing for the low-level Python classes above (`NindLexiconindex`, `NindTermindex`, `NindLocalindex`, `NindRetrolexicon`, and `nind_engine.NindIndexer`'s writer): they delegate their hot-path lookups/writes to it rather than hand-rolling binary parsing. The shared structural-diagnostic base (`NindPadFile.analyseFichierPadFile`/`NindIndex.analyseFichierIndex`, backed by new `NindPadFile::analysePadFile`/`NindIndex::analyseIndex` C++ methods returning structured stats, bound as `analyse_pad_file`/`analyse_index`) is migrated too. The remaining, per-format diagnostic-only methods (the lexicon's and retro lexicon's `dumpeFichier`, `debogueIndex`, `donneCollisions`, `donneMax`, `donneClef`, and each class's own `analyseFichierXxx` beyond the shared base; the term and local indexes' `dumpeFichier`, `afficheTerme`, `afficheDocument` are native, through `get_term_def`/`get_local_def`) still stay on the original pure-Python parsing since `nind._native` doesn't expose that introspection surface yet — see "Planned follow-up work" below.

## Build & test — C++

Requires the `NIND_DIST` env var (install prefix). Build via the wrapper script, not raw `cmake`/`make` directly:

```
NIND_DIST=/path/to/dist ./gbuild.sh              # Debug build (default), builds + installs
./gbuild.sh -t ON                                 # also run ctest (unit tests) before installing; fails on test failure
./gbuild.sh -m Release                            # Release or RelWithDebInfo
./gbuild.sh -a ON                                 # with AddressSanitizer (+ UB/leak sanitizers where supported)
./gbuild.sh -n native                             # -march=native instead of generic tuning
./gbuild.sh -j 1                                  # build with one process (default: one per CPU)
./gbuild.sh -G Unix                               # use Unix Makefiles instead of Ninja
```

Build artifacts land in `build/<git-branch>/<mode>-<asan>/<project>` (isolated per branch/mode, so switching branches doesn't require a clean).

To run tests manually instead of via the full `gbuild.sh` cycle: `ctest --output-on-failure` from inside that build directory.

C++ unit tests live in `tst/cpp/unit/<Module>/` (one executable per library, one ctest entry each) and use **doctest**, vendored as the single header `tst/cpp/unit/doctest.h` (v2.4.12) — no system package or download needed, so they are always built. Each executable accepts doctest options, e.g. `NindIndexUnitTests -tc='NindIndexRobustness*' -s`. Corrupt/hostile-input tests live in the `*RobustnessTest.cpp` files: they patch or byte-by-byte corrupt files produced by the writers and require every read to either succeed or throw a `FileException` — run them under `-a ON` so ASan/UBSan/LSan turn any memory error, UB or leak into a failure. (`-a ON` needs the GCC sanitizer runtimes — `libasan`, `libubsan`, `liblsan` packages on RHEL-like systems.)

Memory-safety conventions in the C++ core (keep them when touching it): readers must never trust a length/offset/count read from a file — bound it against the buffer (`NindFile::get*` check before advancing) or the real file size (`NindFile::getCurrentFileSize()`); byte assembly is done in `uint32_t`/`uint64_t` (never `int`, which overflows); chains read from files (indirection blocks, compound words) must be provably finite; `NindFile`/`NindPadFile` are non-copyable; critical sections use the RAII `NindCriticalSection`, never raw `beginCriticalSection`/`endCriticalSection`; a file has at most one writer — `NindPadFile`/`NindLexiconFile` writers take a non-blocking exclusive `flock` (`NindFile::lockExclusive`, no-op on Windows) and create files with `"w+bx"` (never truncating a file another writer just created), so a second writer, even in-process, gets an exception instead of corrupting the file (readers never lock).

**Thread-safe readers.** Besides the sequential API (one `FILE*`, one read buffer per object: single-threaded), readers have a `const` read path that many threads can use on one object at once: `NindFile::readAt` (positioned reads, `pread`/`ReadFile`+`OVERLAPPED`, on a read-only handle of its own) into a caller-owned `NindReadBuffer` (the bounds-checked decoders, shared by both paths: each format's decoder is written once against a `NindReadBuffer`), `NindPadFile::getEntryPosAt` (the indirection-block map as an immutable snapshot behind an atomic pointer; a reader that misses an entry remaps, under a mutex, only if the file grew), and `const` overloads of `NindTermIndex::getTermDef`/`getTermPostings`, `NindLexiconIndex::getWordId`, `NindLocalIndex::getLocalDef` (its external -> internal id map behind a `shared_timed_mutex`, in both APIs). One thread on the sequential API may run alongside `const` readers of the same object. A file written in place (Amose) can be read while it's written: a rewrite in place may be seen half-written, as by cross-process readers (decoding then fails or, rarely, yields a mix the format can't detect); published Python generations are immutable. In `nind._native`, readers' lookups use the `const` path with the GIL released; `Bm25Scorer` takes scratch arrays (and its read buffer) from a pool; the 8-byte-per-document scores array only for an exhaustive search (MaxScore doesn't use it: it was 1 GB per concurrent search at 138M). `NindSegmentedIndex` reads lengths with `NindDocLengths::readCompact` (mapped, ids left out when consecutive: 4 bytes a document at open, not 24). With `mapLengths` (`NindEngine(map_lengths=True)`; update lookups and `_RecordNames` use it) the scorer reads them in the mapped file (`NindDocLengths::map`, `NindBm25Scorer`'s mapped constructor): no memory of the process's own, searches 3-6% slower (4 KB pages against a copy's huge pages). MS MARCO v2 138M, one index: a search process opens in 1.0 s with 0.52 GiB of its own (6.4 s and 5.15 GiB when names were read whole), 0.85 GiB after queries (6.50). Don't use `thread_local` for buffers in the module: every access may cost a `__tls_get_addr` call, and with LTO the compiler recomputed its address in the decoding loops (11% of a search). Tests: `NindConcurrentReadTest.cpp` (run them under `gbuild.sh -s ON`, ThreadSanitizer, exclusive with `-a ON`), golden v1 files in `tst/cpp/unit/NindIndex/golden/v1` (`NIND_WRITE_GOLDEN=1` regenerates them, for an intended format change only). Windows: the unit tests are POSIX-only and CI builds Windows only when publishing wheels; `tst/cpp/windows/run-under-wine.sh` cross-compiles a smoke test of the const read path with MinGW-w64 and runs it under Wine (8 threads of `readAt` + the sequential API on one object). On Windows, concurrent reads of one handle are serialized by the system: correct, not parallel. Note: `gbuild.sh -t ON -a ON` runs the tests with `ASAN_OPTIONS=halt_on_error=0`, which doesn't fail on leaks; `ctest` in the build directory does.

`-DDEBUG_NIND` is added automatically in `Debug` and `RelWithDebInfo` modes (and in `Release` if configured with `-DWITH_DEBUG_MESSAGES=ON`) to enable conditional debug output.

## Build & test — Python

The Python package (`nind`, in `src/py/nind`) is managed with `pyproject.toml`/`scikit-build-core` (the old `src/py/CMakeLists.txt` build path is kept only for compatibility). `uv sync`/`uv build` compiles `nind._native` (via CMake — see `src/cpp/NindPy/CMakeLists.txt`) and installs the package (editable for `sync`: Python edits are live, but the compiled `_native` is only rebuilt by `uv sync --reinstall-package nind`) plus dev dependencies (pytest) into `.venv`. Building requires a C++14 compiler; `scikit-build-core`, `pybind11`, `cmake`, and `ninja` themselves are all pulled automatically as PEP 517 build requirements (the latter two so builds work even in containers with no system CMake/Ninja, e.g. manylinux in CI) — no manual install needed.

Tests live in `tst/py/` (one file per module, mirroring `tst/cpp/unit/`), configured via `[tool.pytest.ini_options]` in `pyproject.toml`:

```
uv sync                 # first time / after touching pyproject.toml
uv sync --reinstall-package nind   # after any C++ change (src/cpp/**, bindings included): plain `uv sync` doesn't rebuild _native
uv run pytest tst/py -v
uv build                 # produce the platform wheel (nind-*.whl) + sdist in dist/
```

`src/cpp/NindPy/CMakeLists.txt` is a standalone CMake project (separate from the top-level `CMakeLists.txt`/`gbuild.sh` flow) that compiles the relevant `NindBasics`/`NindRetrolexicon`/`NindLexicon`/`NindIndex` sources directly into the `_native` extension module — not linked against the shared libraries `gbuild.sh` produces — so the wheel ships one self-contained `.so` with no internal RPATH/dlopen. It is not wired into `gbuild.sh`/ctest; touching the core C++ sources may require rebuilding both independently.

The current test suite validates the Python implementation against itself (round-trips through `nind_engine.NindIndexer`'s writers, plus hand-built fixtures for formats it doesn't write, like `.nindretrolexicon`), not against separately-produced C++ binary files — the Python and C++ implementations aren't an intentional independent cross-check of each other (see `## Binary format verification` below).

### Releasing

Version bumps are managed by `bumpver` (config: `[tool.bumpver]` in `pyproject.toml`) — it keeps `current_version` (git-tag form, `vX.Y.Z`) and the PEP 440 form in sync everywhere it appears: `[project] version` in `pyproject.toml` and every `__version__ = "..."` across `src/py/nind/`. Its `pre_commit_hook` (`cicd/bumpver-pre-commit.sh`) runs `uv lock` and adds `uv.lock` to the version's commit (a pattern can't tell nind's entry there from another package's). Cutting a release is:

```
uvx bumpver update --patch    # or --minor / --major; add --dry to preview first
```

This commits, tags (`vX.Y.Z`), and *pushes* in one step (`push = true` in config) — pushing the tag is what kicks off `.github/workflows/publish-pypi.yml`, which builds wheels for Linux/macOS/Windows (via `cibuildwheel`, using `uv` as its build frontend) plus an sdist (`uv build --sdist`), and publishes them to PyPI with `uv publish --trusted-publishing always`. That workflow authenticates via PyPI Trusted Publishing (OIDC) against the `pypi` GitHub Environment — no stored token — but this only works once the `nind` PyPI project has that repo+workflow+environment registered as a trusted publisher (pypi.org project settings → Publishing); until then the `publish` job's `id-token` exchange will fail.

## Architecture

**Everything in the C++ API.** Amose and other clients use nind through its C++ libraries only: new logic (builders, updates, merges, scoring, pruning, verification) goes into a `NindIndex`-family class, with doctest tests in `tst/cpp/unit/`. `src/cpp/NindPy/bindings.cpp` only converts types and releases the GIL; Python only orchestrates (tokenizer choice, the generations and their publishing, the names and lengths side files).

### C++ library layering (`src/cpp/`)

Each subdirectory builds one shared library; dependencies flow strictly downward (see each module's `CMakeLists.txt` `target_link_libraries`):

```
NindBasics   (no deps)      — NindFile: buffered binary sequential file I/O; NindPadFile: ident <-> data mapping on top of it
   ^
   ├── NindRetrolexicon     — flat-file reverse lexicon (id -> string)
   ├── NindLexicon          — in-memory lexicon (asymmetric maps), NindLexiconFile for its on-disk form
   │
NindIndex (deps: NindBasics, NindRetrolexicon)
   — NindLexiconIndex/NindLexiconIndexK: lexicon as an index file (K variant uses two 32-bit keys instead of strings)
   — NindTermIndex: the inverted file itself, as an index file
   — NindLocalIndex: per-document local index file
   — NindIndex: ties the above into a full inverted/local index file
   — NindIndexMerge: offline merge of index shards (disjoint documents) into one standard index
   — NindTokenizer: tokenizer for source-code-like text (used by the Python indexer)
   — NindDocNames: document id <-> name file of an index (.ninddocnames)
   — NindDocIdMap: compact external -> internal document ids of NindLocalIndex (header only)
   — NindIndexBuilder: bulk build of the term and local index files from batches of term ids
   — NindIndexUpdate: incremental updates (add/replace/remove documents; touched terms only)
   — NindBm25Scorer: BM25 search, exhaustive or block-max MaxScore (same results)
   — NindSegmentedIndex: an index of immutable segments searched as one; NindDocLengths, NindSegmentDeletes (side files)
   — NindSegmentedUpdate: a new segment, deletions masked, log-structured merges
   — NindIndexVerify: checks an index of either format, reports instead of throwing

NindAmose (deps: NindIndex, NindRetrolexicon)
   — adapts nind to Amose's richer term-type model (see internal doc refs "LAT2015.JYS.448")
   — NindAmoseMerge: NindIndexMerge for Amose indexes (retro lexicon, recomputed term counters)

NindPy (deps: NindBasics, NindRetrolexicon, NindLexicon, NindIndex sources, compiled in directly)
   — pybind11 bindings, built only through the Python wheel (scikit-build-core), not gbuild.sh
```

All C++ code lives in namespace `latecon::nindex`. Class/file naming mirrors the binary format they implement (e.g. `NindLexiconIndex` reads/writes the `.nindlexiconindex` file format) — this naming convention holds across both the C++ and Python trees, so a class name tells you both its role and its file extension.

Design docs are referenced by internal report codes in file header comments (e.g. `LAT2014.JYS.440` = "nind, indexation post-S2", `LAT2015.JYS.448` = "Adaptation de l'indexation nind au moteur de recherche Amose") — these aren't in the repo, so treat the header comments above each class as the closest available spec.

Linker flags (`-Wl,-z,defs,--no-as-needed`) are set project-wide because these libraries are loaded dynamically via a plugin/factory mechanism, so symbols must stay visible even when not directly referenced by the linking binary — don't "clean up" apparently-unused exports without checking for this.

`tst/cpp/` mirrors the module structure for test binaries, but note `tst/cpp/CMakeLists.txt` currently only builds the legacy `NindIndex`, `NindSearch`, and `NindAmose` test programs (not registered with ctest) — the `NindLexicon`, `NindTests`, and `NindBasics` legacy subdirectories are commented out. The ctest-registered unit tests are in `tst/cpp/unit/` (always built, see above).

`src/cpp/NindIndex/NindLexiconIndexK.{h,cpp}` is dead code: not in any CMake target, and it no longer compiles against the current `NindPadFile` API.

### Python package (`src/py/nind/`)

Parallels the C++ layering with lowercase-suffixed module names for the index classes:

- `NindFile.py` — low-level binary codec. Historically read-only-oriented (the `litXxx` getters have long existed for every format), but now has a full writer counterpart too: `ejcritNombre1/3/4/5`, `ejcritNombreULat`/`ejcritNombreSLat` (both varint encodings, full tier range matching the readers and the C++ implementation), `ejcritChaine`, `ejcritZejros`.
- `NindPadFile.py` — the shared "pad file" envelope (header, indirection block(s), specifics, identification trailer); read-only, no writer (mirrors `NindBasics::NindPadFile`, but nothing in Python subclasses it as a writer the way `NindIndex`/`NindRetrolexicon` do in C++).
- `NindRetrolexicon.py`, `NindLexiconindex.py`, `NindTermindex.py`, `NindLocalindex.py` — ergonomic read-only Python wrappers around the corresponding `NindIndex`-family C++ classes; their hot-path lookups delegate to `nind._native`, as does the shared structural-diagnostic base (`analyseFichierPadFile`/`analyseFichierIndex`, inherited from `NindPadFile.py`/`NindIndex.py`). The remaining, per-format diagnostic/analysis methods (the lexicon's and retro lexicon's `dumpeFichier`, `debogueIndex`, `donneCollisions`, `donneMax`, `donneClef`, and each class's own `analyseFichierXxx` beyond the shared base; the term and local indexes' `dumpeFichier`, `afficheTerme`, `afficheDocument` are native, through `get_term_def`/`get_local_def`) remain hand-rolled pure-Python parsing, since `nind._native` doesn't expose that introspection surface yet (see "Planned follow-up work" below). `NindLexiconindex` is hash-bucketed (`clefB(word) % nombreIndirection`), the other two are directly indexed by id.
- `nind_engine.py` — `NindIndexer` (writer) and `NindEngine` (BM25-style search) built on top of the above. `NindIndexer` is the *only* Python writer for the index-family formats (`.nindlexiconindex`/`.nindtermindex`/`.nindlocalindex`) — it builds them via `nind._native`'s `is_writer=True` constructors. It does not write `.nindretrolexicon` (not needed by `NindEngine`, which only supports simple, non-compound words). `NindIndexer.index_jsonl` reads pyserini's JSON Lines corpus format (`{"id": ..., "contents": ...}` per line; record n = document n; the record ids are returned and stored as document names, see below) — worker processes each parse a line-aligned byte range of the file. Tokenization is native (`NindTokenizer`, bound as `nind._native.Tokenizer`; options `tokenizer=` of `NindIndexer`, see `TOKENIZER_DEFAULTS`: each identifier split optional, ASCII lowercasing, tokens over 254 bytes — the lexicon's limit, `NindFile::putString` — dropped); a subclass overriding `_default_tokenize` falls back to Python token lists (`_chunk_from_token_lists`). Indexing is parallel but every file keeps a single writer: worker processes tokenize chunks of documents with `Tokenizer.tokenize_batch`, which returns the chunk's vocabulary plus uint32 term ids/ends (cheap to pickle); the parent writes the lexicon with one `add_simple_words` call (`NindLexiconIndex::addWords`: each hash bucket written once), feeds the chunks to `nind._native.IndexBuilder` (`NindIndexBuilder`, C++ API; remaps chunk ids to term ids), which writes the term and local index files from two threads with the GIL released. Every writer of a new generation runs in bulk mode (`begin_bulk`/`end_bulk`, `NindIndex::beginBulk`: no per-write flush/seek/signal handler, indirections and tail written once — byte-identical files). The local writers split a term's positions into entries of ≤255 (`<nbreLocalisations>` is one byte). `local_index=False` leaves the local index out. Each generation also holds `<prefix>.nindmeta` (JSON: tokenizer options, local index or not) and `<prefix>.ninddoclengths` (binary: `NINDDL01`, count, doc ids, lengths): `NindEngine` reads document lengths from it (no local index needed) and tokenizes queries with the stored options; indexes without them (older versions) are read from their local index and queried/updated with the original regex tokenizer (`LEGACY_TOKENIZER`). Document names (the corpus's own ids: `index_jsonl` stores the records' ids, `index_files(doc_names=...)` given names, updates take `name=`; a known name without `doc_id` replaces that document) go in `<prefix>.ninddocnames`, the `NindDocNames` C++ format (`src/cpp/NindIndex/NindDocNames.h`: written once, mapped (`NindMappedFile`, `NindBasics`: page cache, shared between processes, not the process's memory; opening checks the header and the arrays' sizes, each lookup the bounds of what it reads, `check()` — run by `verify_index` and by `merge` on each shard — the whole file), `NindDocNames::merge` for shards, `write` from packed names (bytes and lengths) for consecutive documents; ids omitted when consecutive, names blob + offsets, a name-sorted permutation for name -> id by binary search; unique names, `std::invalid_argument` -> `ValueError` otherwise); `NindEngine.doc_name`/`doc_id`, `search(..., doc_names=True)` returns names like pyserini's `docid`. `NindEngine.search` is driven by the postings lists: `nind._native.Bm25Scorer` (`NindBm25Scorer`, C++ API; built once per opened generation from the document lengths) reads each distinct query term's postings once (`NindTermIndex::getTermPostings`: flat vectors, no allocation per posting) and scores only the documents in them (flat arrays indexed by the document's position in the corpus, no hashing per posting: ~10 ns per posting), with the formula of `NindEngine._bm25_score` (the per-document `bm25_score` stays in Python; scores equal to rounding, not bit for bit: tests compare them with a 1e-9 relative tolerance; MaxScore and the exhaustive search return identical results), ties kept in index order. A small top k (`top_k * PRUNING_DOCS_PER_RESULT <= documents`) goes through block-max MaxScore instead (`Bm25Scorer.search(prune=True)`, `searchMaxScore`: over format v2 block descriptors, document at a time for up to 4 terms (`scanRangeByDocument`), from 5 terms in windows of at least 4096 documents scored term at a time into a dense array (`scanRangeByWindow`: MS MARCO v2 138M, 9+ terms 300 -> 137 ms, mean 37.7 -> 29.8 ms, Lucene 35.9; fewer terms are faster document at a time, unless their blocks are dense: 8 or more per 4096 documents on average, a stopword's list, also by windows), comparisons with theta under a 1e-9 margin, candidates rescored exactly in query order: identical results; see `docs/proposals/format-v2-blocks.md`, step 6). Every build goes into a new generation directory published atomically (see `_index_store.py` below), so rebuilding never disturbs readers. With `shards=N` it instead builds N independent indexes over contiguous parts of the files in worker processes (in a temporary directory inside the new generation), then merges them with `nind._native.merge_indexes`; `index_jsonl(shards=N)` does the same over line-aligned parts of the file (each worker parses its part in pieces of `JSONL_SHARD_PIECE_BYTES` and writes its index, lengths and names; the parent only concatenates arrays and calls `NindDocNames.merge`; it returns a lazy `_RecordNames` sequence, strings read from the names file, not a list). A sharded build is faster than a direct one and bounds the memory: this is the documented route past ~10M documents (see "Sharded indexing" below); `index_jsonl(memory_gb=X)` picks the fewest shards (and, if needed, fewer workers) whose builds fit in X, from the tokens, postings, documents and distinct terms of a few samples of the file and a model of a build's memory (`NindIndexer.BUILD_BYTES_PER_TOKEN`/`_PER_POSTING`/`_PER_DOCUMENT`/`_PER_TERM`/`_PER_PROCESS`, the postings counted in the samples as each document's distinct terms, a build's vocabulary extrapolated with `HEAPS_EXPONENT`), counting the parent beside the workers; the names check after them is `NindDocNames::checkUnique` (each shard's `check()`, then their name orders merged through a heap: nothing per document, nothing written; it was a merge to a file then removed, 2.6 GiB at 138M); pool workers call `malloc_trim` after each shard (`_release_freed_memory`: glibc kept 0.4 GiB of a 3M-document shard, which the worker's next shard started from). A build's memory: `NindIndexBuilder` holds 4 bytes per token and 16 per document (reserved up front) and writes the term index from 5 bytes per posting (32-bit document positions, 8-bit frequencies, larger ones apart), a range of terms at a time if given a budget (`IndexBuilder.postings_budget`, `NindIndexBuilder::setPostingsBudget`: the tokens scanned once per range, the same file; the planner uses up to `MAX_BUILD_PASSES` = 4, the fewest that fit, before more shards); tokenizer batches are packed (`Tokenizer.tokenize_batch_packed`: the words' bytes and their ends, no Python string per word), the builder numbers their words (`IndexBuilder.add_batch`, ~50 bytes a distinct word) and writes the lexicon (`write_lexicon`, through `NindLexiconIndex::addSimpleWords`: a new lexicon given sorted unique words writes each hash bucket from its words alone, ~8 bytes a word where `addWords` held ~400, 4.6x faster; the same file); `_write_chunks` frees each tokenized chunk once added; the record ids are packed by the workers (`_PackedNames`: their bytes and lengths, ~24 bytes a document where a list of `str` took ~80) and written before the build (`NindDocNames.write_packed`, `NindDocNames::write` from packed names: streamed, 12 bytes a document besides them), and `index_jsonl` returns them as `_RecordNames`, read from the names file (a direct build with ids that aren't all strings still returns a list of them); the planner aims at `MEMORY_GB_MARGIN` (90%) of the budget: equal shards started together peak together. Incremental indexing goes through `NindIndexer.update()` → `IndexUpdate` (shortcuts `add_file`/`add_files`/`remove_documents`). It is a context manager that, under the writer lock:
1. hard-links the published generation's segments into a new one (`IndexStore.link_generation`; an index of one piece becomes one segment), keeping its tokenizer options and whether it has a local index (explicitly different `NindIndexer` arguments are refused);
2. collects adds, replacements and removals in memory, opening the published index only for what needs a lookup (a given id, a name): no whole-corpus structure in Python;
3. on exit, hands them to the C++ API, `nind._native.SegmentedUpdate` (`src/cpp/NindIndex/NindSegmentedUpdate.{h,cpp}`), then publishes. `IndexUpdate.add_jsonl` is the batch path: worker processes parse and tokenize (as `index_jsonl`), and each tokenizer batch goes to `SegmentedUpdate.add_documents` with nothing per token in Python; `NindSegmentedUpdate` keeps documents as ids of its own vocabulary (each word hashed once), and its merge policy reads segment counts from the side files' headers. MS MARCO v2 138M, +1.38M passages: 12.4 s (Lucene 11.6 s). `NindTermIndex::setDocumentLengths` keeps a dense table from the first id (a segment of an update or shard starts far from 0; it was a binary search per posting).

**Segments** (`docs/proposals/segments.md`, `NindSegmentedIndex`, `NindSegmentedUpdate`). An index is either one piece or a manifest `<prefix>.nindsegments` naming `seg-<n>-<hex>/` directories, each a standard index plus its lengths, names and `.ninddeletes`. Sharded builds keep their shards as segments (`merge=True` for one index). A commit writes a new segment and masks replaced and removed documents; merges are log-structured (`IndexUpdate.MERGE_FACTOR`, `MAX_MERGED_DOCS`: a tier's smallest that fit under it; at half of it a segment is full, left alone, so the count stays bounded; a segment over half deleted is rewritten alone); `NindIndexer.force_merge` makes one. `NindEngine` searches through `SegmentedIndex`: N, average length and every df are the live documents' (per-term counts in `.ninddeletes`), theta is shared between segments, ties go by increasing id, so results are those of one index built from the live documents; tests hold every commit to it. Opened segments are shared across generations by name. `NindEngine.lexicon`/`term_index`/`local_index`/`get_term_id` raise `ValueError` on several segments or deletions.

**Costs.** On MS MARCO 8.8M: +88k documents 2.6 s (17.6 s when it merges 9 of a 16-shard build, once), +1 0.3 s, -100 0.8 s, `force_merge` 24–35 s; a build with 8 or 16 shards 25 s vs 46 s direct; top 10 latency p50 1.57 ms (1 segment), 1.82 (8), 2.65 (32) on one thread, 0.77/0.74/0.90 on 8; `update.stats` tells what a commit did.

`NindIndexUpdate` (`src/cpp/NindIndex/`) stays for C++ clients writing one index in place (Amose): it migrates a v1 index first, finds a replaced or removed document's terms from the local index or by scanning, updates each touched term with `NindTermIndex::updateTermDef` in bulk mode (a term that only gains documents rewrites its last block, the new blocks and its directory in place, in the room an earlier rewrite left), and rebuilds when the lexicon is too full (`lexiconMaxLoad`). Python no longer uses it.
- `_index_store.py` — the on-disk layout that makes every `NindIndexer`/`NindEngine` operation safe without the caller doing anything: each build writes a fresh, never-modified generation directory `<prefix>.gen-<n>-<hex>/`, flushed to disk (`fsync`) then published by atomically replacing the pointer file `<prefix>.CURRENT` (a pointer file rather than a symlink: atomic on Windows too). Readers open every file of the generation `CURRENT` names under a shared `flock` on its `generation.lock` (only while opening: open files stay readable after deletion on POSIX); `NindEngine` checks `CURRENT` (one `stat`) at the start of each public call and switches to a newly published build, each call answering from one snapshot (`_Snapshot`; nested public calls of a thread reuse their caller's, a `threading.local`); calls from several threads run in parallel (the native readers' lookups are thread-safe and release the GIL, see "Thread-safe readers" below), the lock only covers switching to a new build. Writers of one prefix are serialized by `<prefix>.lock`; after publishing, the writer deletes older generations nobody is opening, crashed builds' leftovers, and flat files of indexes written before generations existed (still readable: no `CURRENT` = flat layout). A failed build never touches `CURRENT`. Lock fds are closed in forked children (`os.register_at_fork`) — otherwise a worker outliving a killed writer would keep the index locked forever — and `NindIndexer`'s pool workers exit when their parent dies. Windows: `msvcrt` locks are exclusive only, so readers don't lock and rely on retrying; generations still open can't be deleted and are retried at the next build.
  A generation's segments are hard links to the previous generation's files: only the new files cost anything, each generation stays complete by itself; files changed in a generation (`.ninddeletes`, the manifest) are removed then created, never written through a link.
- `Nind_*.py` at the package root — standalone CLI scripts (dump a document, convert corpora, search, diagnostics)
- `amose/` — Amose-specific conversion/parsing scripts (Lucene dump, XML-CLEF, sample corpora)

## Binary format verification

Binary file formats are specified in EBNF grammar (see README). The Python package reads/writes these formats either through `nind._native` (the compiled C++ implementation itself, via pybind11) or, for the diagnostic-only tooling not exposed by those bindings, through hand-rolled pure-Python parsing that must stay in sync with the grammar at the file-format level. There is no intentional independent-reimplementation-for-cross-verification design here — that framing in earlier notes was a misunderstanding of the project's actual intent, which was simply to give Python callers an ergonomic interface.

**Format v2 (written by default) and v1 (still read).** Writers write format v2 (`docs/proposals/format-v2-blocks.md`: its "v2 grammar" section is the spec; the EBNF comments in the C++ sources still describe v1). The version is identified by the pad-file entry size (`NindIndex::isFormatV2`, bound as `is_format_v2`: 10-byte indirections = v2, 8 = v1). In v2:
- **Fields**: definition offsets are 6 bytes and lengths 4; local-index and lexicon header fields are 4 bytes; external document ids are 64 bits (`NindDocId`, `EntierULat64`; `NINDDL02`/`NINDDN02` side files).
- **Blocks**: a term's category of more than `NindTermIndex::BLOCK_SIZE` (128) postings is cut into blocks after the term's directory (per-block first/last doc, count, max frequency, min length; offsets relative to the definition).
- **Readers**: `getTermDirectory`/`getTermBlocks` read a directory alone, then only the blocks needed (`Bm25Scorer`'s MaxScore).
- **Limits**: internal numbering stays 32 bits (≤ 4.29G documents per index; 64-bit internals are a "possible evolution" in the proposal).

v1 files (older nind, Amose's legacy indexes) are read by every reader. A writer refuses to extend one (`"format v1 file, written by an older nind: rebuild it"`). `IndexUpdate` does that rebuild itself: it merges the copied v1 generation onto itself before applying its changes, about the cost of a full rewrite, once (fixtures: `tst/py/data/v1`, generations and flat layout). `NindIndexVerify::verify` (bound as `nind._native.verify_index(base, cross_check=False)`, returning a `VerifyReport`) checks an index of either format without throwing. It checks: lexicon entries; the pairing of the files; every definition, through both read paths; lists increasing, frequencies summing up; v2 block descriptors against their blocks (what MaxScore trusts when it skips a block); local documents; and optionally the term vs local (document, term, frequency) triples. Golden files: `tst/cpp/unit/NindIndex/golden/v1` (read only) and `golden/v2` (writers must reproduce them).

**Sharded indexing — offline merge implemented; follow-ups below.** Nind files are single-writer by design (no locking, readers resync lazily; see `NindPadFile::getEntryPos`), and every write rewrites the shared specifics/identification tail at EOF, so concurrent writers on one file would serialize anyway — sharing a file between writers is explicitly *not* the plan. Writes scale instead across N independent shards (each its own lexicon + term + local files, one single-threaded writer each, over a partition of the documents), kept as the index's segments and searched as one (the default, see "Segments" above; decided 2026-11-05: performance first, Amose adapts), or merged offline into one standard index that every existing reader uses unchanged (`merge=True`, `force_merge`).

How the merge works (`NindIndexMerge`, `src/cpp/NindIndex/`): shard lexicons are enumerated with `NindLexiconIndex::getEntries` (walks the hash buckets; no retro lexicon needed) and unioned with words canonicalised as (union id of the prefix, last component) — which also gives the exact merged size, used as the lexicon's hash modulo; documents are listed with `NindLocalIndex::getDocIdents` and checked disjoint *before anything is written* (shards without local index — all or none — give a merged index without one; a document in two shards then only shows up as a duplicate in a shared term), merged files are written in bulk mode with a single `addWords`; each merged term's postings are gathered from every shard (per term, so memory stays small) and each document is copied with its term ids remapped (local term order is kept, so Amose's per-occurrence reading order survives). A failed merge removes the target files. `NindAmoseMerge` (`src/cpp/NindAmose/`) forces a retro lexicon and recomputes the 8 term counters, a term's type being derived from its components as in `NindLexiconAmose::getWord` (unique-term counts aren't additive across shards); they're written once at the end with `NindTermIndex::setSpecificWords`. The plain merge refuses shards with term specifics.

**At hundreds of millions of documents.** What grows with the corpus stays flat: `NindTermIndex::setTermPostings` writes a term from flat postings (byte-identical to `setTermDef`; used by `NindIndexBuilder` and the merge) with a buffer bound exact for bit-packed blocks (the former 14 bytes per posting capped a term at ~306M documents; now the 4 GiB definition, about 4G postings); the merge concatenates shards' postings and sorts only when documents interleave, and checks shards' document ranges without a global sort (interleaved shards fall back to it); `NindDocIdMap` (4 bytes per document for consecutive ids, 12 increasing, a map otherwise) replaces `NindLocalIndex`'s `std::map`; `NindDocNames::merge` streams the merged names, `NINDDN03` (8-byte offsets, only for names over 4 GiB); `NindIndexVerify` reads flat (the list paths only on definitions of at most 1M postings); `_Snapshot` holds no per-document Python structure (`NindBm25Scorer`: no id table for consecutive ids, 2 or 4 bytes of length); a `NindLocalIndex` reader fills its id map at its first lookup, not when opened (a corrupt document header then shows up there). Measured: `bench/README.md` section 6, and on a real corpus of 138M documents (MS MARCO v2) in section 7; what's left is in `docs/TODO.md`.

Follow-ups:
- **Merge cost is I/O-syscall bound, and so are all writes** — largely addressed for writers of new files by bulk mode (`NindIndex::beginBulk`, used by `NindIndexer` and `NindIndexMerge`; a 10k-document build went from ~1.9M to ~0.2M syscalls, the rest being the input files). Still open: Merging 10k documents / 58k terms from 4 shards makes ~2.3M `lseek`, ~1.5M `read`, ~280k `write` and ~250k `rt_sigaction` calls: `NindIndex::getDefinition` discards the stdio buffer (`flush`) then seeks+reads twice (indirection, then data) on every read, `NindFile::writeBuffer` flushes every write, and every critical section installs/restores a signal handler. A direct build pays the same per definition, so a merge costs about a full rewrite. Reading with `pread` (one syscall per read, no buffer discard) and a bulk mode for a writer creating a fresh file (no per-write flush, tail written once) would speed up merges, direct builds and search alike — mind the reader-resync semantics above when touching this.
- **CLI for Amose/LIMA** multi-process indexing: a small C++ program (like the legacy `tst/cpp/NindAmose/` tools) running `NindAmoseMerge` over shard prefixes. `NindAmoseMerge` isn't bound in `nind._native` (the wheel doesn't compile `NindAmose`).
- `NindLexiconAmose::getWord` dereferences past the end of the component list for the lexicon word `§` alone (the first prefix of every named entity): undefined behaviour, seen as a `bad_alloc`. Normal lookups never ask for that id; the merge doesn't call `getWord`.
